上下文预算与压缩：长会话为什么会中途崩掉

为什么学这个：在 2026 年的 Agent 岗面试里，上下文管理是真题密度最高的一簇，字节、蔚来、 阿里云、小红书都问过同一类问题：压缩放在链路哪一步、怎么保证不丢关键内容、快到窗口阈值时 怎么不打断用户。你的项目里已经有一份可讲的实现（backend/core/agent/context.py）， 这节课的目标是把这份实现讲成一套有取舍的工程判断，而不是复述参数。

一、问题：窗口是硬的，会话是软的

大模型 API 是无状态的。每一轮请求，你都要把完整历史重新发一遍——上一轮发过的内容， 这一轮还得再发。于是输入长度随轮次单调增长，而窗口是死的上限。三个增长源按体积排序，通常是： 工具结果（一次网页抓取、一份文件全文）、助手侧推理过程、用户往返文本。

更麻烦的是，真正卡住你的往往不是标称窗口，而是上下文腐烂：窗口里塞的 token 越多， 模型准确取回其中某条信息的能力越差。原因是注意力在 n 个 token 上形成 n² 的两两关系。Anthropic 的 上下文工程文章把它写得很克制——这是性能梯度，不是悬崖，所以工程目标落在「给出最小的高信号 token 集合」。

随着上下文窗口中 token 数量增加，模型从该上下文中准确回忆信息的能力会下降。每一个新引入的 token 都会消耗一部分注意力预算。 —— 摘译自 Anthropic · Effective context engineering for AI agents（2025-09-29）

既然总量必然增长，工程上的共同做法就是把窗口总额切成几段预留，不等撞上限才反应。 下面三个开源 agent 的默认值口径各不相同，但都留出了非零余量：

样本 触发点 保留区 预留
opencode v2 输入上限减 buffer 15,000 tokens buffer 20,000
DeepAgents 窗口的 0.85 窗口的 0.10 由两者之差隐含
Codex 配置项前缀减预留 用户消息原话留 计价范围可选
数据与取舍的完整版见笔记库模式卡 02（路径见文末「本课主资源」），本讲义只取教学所需的对比。

二、你的项目现在怎么做：一前一后两档

backend/core/agent/context.py 里有两道工序，顺序固定，成本差别巨大：

第一档 · 结果驱逐（T1.4）——纯机械操作，零额外模型调用。单条 tool 消息的 content 超过阈值时，只把 content 换成「占位标记 + 工具名 + 原文字符数 + 留痕指针 + 头尾预览」。 注意措辞：换内容，不删消息。

# backend/core/agent/context.py — 占位符的构造（节选）
placeholder = (
    f"{EVICT_PLACEHOLDER_PREFIX} | 工具: {name} | 原文 {len(content)} 字符 | 留痕: {ref}]\n"
    f"--- 头部预览（前 {head_chars} 字符）---\n{content[:head_chars]}\n"
    f"--- 尾部预览（后 {tail_chars} 字符）---\n{content[-tail_chars:]}"
)
📄 backend/core/agent/context.py 的 evict_tool_results()（只读引用，教学不改）

为什么不能整条删掉？代码注释里给了直接原因：OpenAI 要求 tool 回复与它的 tool_call_id 保持配对，删了这条消息，请求本身就是非法的。这是接口约束，不是优化选择。

第二档 · 历史压缩——在每次调用大模型之前执行。总量越过预算时，丢掉早期消息， 保留最近若干条原始消息，并按配置决定丢弃的方式：

# backend/core/agent/context.py — 截断分支的产物（节选）
placeholder = {
    "role": "system",
    "content": f"{PLACEHOLDER_PREFIX}{dropped}{PLACEHOLDER_SUFFIX}",  # 「[上下文已截断：前 N 步历史已省略]」
}
result = [placeholder, *keep_msgs]            # 摘要策略则把 placeholder 换成模型摘要
📄 _compress_truncate() 与 _compress_summarize()；两者共用 keep_recent 与「至少保留 2 条」的下限

两档的实际参数都在 backend/config.py：

档位 参数 默认值
结果驱逐 context_evict_threshold_chars 4000（单条）
context_evict_protect_recent 10（按位置）
context_evict_head_chars 800
context_evict_tail_chars 400
历史压缩 context_token_budget 32000（估算口径）
context_keep_recent 10（条消息）
context_compress_strategy truncate（零额外调用）
context_summary_max_tokens 300（仅 summarize 用）
三条容易被忽略的实现细节，都是面试可讲的点：

① 不足预算时返回原对象（identity），不复制列表——两档都遵循这个约定，配合调用方可跳过无谓处理。

② 驱逐是幂等的：占位符已存在就跳过。因为每次调用大模型前都会重跑这一遍。

③ 保护是位置性的、不看角色：protect_recent=10 保护的是最后 10 条， 最新的尾巴永不被驱逐。这样助手的工具调用与它的结果不会被拆开。

五、检索练习（本课作业）

凭记忆完成，别翻讲义

练习 1 · 报数：不看代码，说出第一档的四个参数名与默认值，以及第二档的三个。

展开对照 第一档：context_evict_threshold_chars=4000、context_evict_protect_recent=10、 context_evict_head_chars=800、context_evict_tail_chars=400。 第二档：context_token_budget=32000、context_keep_recent=10、 context_summary_max_tokens=300（后者仅 summarize 策略使用）。 数不出来不要紧，要紧的是知道「两档各有独立阈值」这件事。

练习 2 · 判断档位：三个场景，各走哪一档？
① 一次 web_fetch 返回 30,000 字符，刚发生，是最近的第 2 条消息。
② 一次 web_fetch 返回 9,000 字符，位于历史中段（离最新消息 40 条）。
③ 会话跑了 60 步，累计估算 41,000 tokens，每条消息都不大。

展开答案 ① 都不动。它落在最后 10 条的位置保护区内——驱逐不看它多大，只看它在哪。
② 走第一档。超 4000 字符且在保护线之外，换成头 800 / 尾 400 的预览加指针，消息保留。
③ 走第二档。没有单条超阈值，但总量越过 32000，丢早期消息、保留最近 10 条。 第一档治「单条太胖」，第二档治「整体太长」，两者的触发条件互不替代。

练习 3 · 找缺口：打开 backend/core/agent/context.py 的 evict_tool_results()， 找出「卸载了但模型没法取回」的证据，写出你会补进去的那一句话。

展开提示 看占位符里的 ref 变量：只有 trace 指针，没有「用什么工具、怎么读回来」。对照样本仓库 （如 DeepAgents）的做法，替代消息里会显式告诉模型用带 offset 与 limit 的读工具分段取回。 补的那句话大意是：「用 read_file(trace_path, offset=N, limit=K) 分段读回全文」—— 没有这句话，卸载与丢弃对模型而言没有区别。

六、面试弹药：30 秒话术（v1）

「上下文这块我拆成两件事：还没进来的和已经进来的。大结果在工具返回那一刻就做卸载， 上下文里只留路径加首尾预览，模型要用再按 offset 和 limit 分段读回来，这样它不占常驻空间而且可恢复； 已经积累的历史才谈压缩，压缩分两档，先做机械缩减——截旧的工具调用参数、丢中间步骤，零额外调用而且确定性， 不够再上模型摘要。摘要必须配硬规则，路径、命令、报错原文、未解决的用户请求要原话保留， 用户消息我一般不摘要、原样留着，因为它是意图的唯一来源。触发点不贴窗口上限，要留 buffer。 另外压缩要建模成可观测的节点，有事件、能中止，不要悄悄截断。」

面试官会往哪追问：他大概率会问「你项目里真做了吗」——这时你要能立刻报出 context.py 的两档参数与顺序（机械档在前），并主动交代你识别出的两个缺口： 占位符没给取回方式、32000 贴着估算口径没留缓冲。 主动说缺口，比被问出来强得多——它证明你真的读过自己的代码，而不是背了别人的方案。
