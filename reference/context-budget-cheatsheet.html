上下文预算与压缩速查

两档对照（本项目默认值）

档位触发条件动作成本
第一档
结果驱逐
T1.4		 单条 tool 消息 content > 4000 字符，且位于最后 10 条之外 换 content：占位标记 + 工具名 + 原文字数 + 留痕指针 + 头 800 / 尾 400 预览。消息保留 零额外模型调用，纯机械、确定性
第二档
历史压缩		 估算总量 > 32000 tokens（口径 chars/4），或条数超 context_max_messages 丢早期消息，插入截断占位符或模型摘要（≤ 300 tokens），保留最近 10 条原始消息 截断零成本；摘要多一次模型调用且失真

顺序固定：驱逐先于压缩，且都在「下一次调用大模型之前」执行。机械步骤先做，能减少送进摘要的体积。

判断流程（看到现象 → 走哪一档）

问题判断与去向
这条消息在最后 10 条里？在 → 什么都不做。位置保护优先于体积判断，驱逐不看它多大。
单条 tool 结果超 4000 字符？超 → 走第一档，换头尾预览。不足 4000 → 不动。
头 800 + 尾 400 ≥ 原文长度？是 → 跳过。预览装不下任何东西时，替换不省空间。
总量超 32000 tokens？超 → 走第二档。不超 → 原对象返回（identity，不做任何复制）。
剩余消息不足 10 条？keep = max(2, min(keep_recent, n))。下限 2 条，压缩不会把历史清空。

三条可直接抄的摘要硬规则

抄自开源 agent 的摘要提示词（完整出处见模式卡 02）。自己的摘要是丢是留，全看这三条有没有写进去：

规则为什么
精确保留文件路径、符号、命令、报错原文、URL、标识符这些是可以被逐字复用的东西，摘要时改写一个字就失效
只带未解决的用户请求，且保留原话已解决的问题不必占额度；原话是意图的唯一来源，转述会引入偏差
保留工作流状态（未提交 / 已提交 / 已推送 / 评审中 / 已合并）状态决定下一步动作，丢了它等于让接手的模型重做一遍

一条更省事的经验做法：压缩后附上最近访问的 5 个文件。用户消息本身不进摘要、按原话保留，摘要只承载助手侧的过程。

本项目待补的两个缺口

缺口证据补法
卸载了但取不回 占位符里只有 ref（trace 指针），没有「用什么工具、怎么读」 在占位符里加一句读回指令：用带 offset 与 limit 的读工具分段取回原文
阈值贴着上限，没留缓冲 context_token_budget = 32000 是按 chars/4 从 128K 窗口保守折算，无额外余量 改成「上限减预留」，单次大结果不会把窗口顶穿
摘要块位置 摘要作为 system 消息插在保留消息之前 对照样本做法：摘要留在末尾，规范上下文贴在最后一条真实用户消息之前

术语表

术语定义
上下文预算把窗口总额切成输出额度、工具占用、原样保留的近期历史、压缩缓冲几段预留。预算是政策，压缩是执行
上下文腐烂
context rot		窗口内 token 增多时模型准确取回信息的能力下降；成因为注意力的 n² 两两关系，属性能梯度而非硬悬崖
压缩 compaction把已发生的消息历史替换成更短的表示
机械缩减确定性压缩，按 token 或条数丢弃、按参数长度截断，零额外模型调用
模型摘要调用另一个模型把旧历史压成结构化摘要，有损且多一次调用
上下文折叠 folding在子任务边界只保留结论、丢掉中间步骤；由任务结构触发，不等窗口压力
保留区 keep压缩后原样保留的近期消息条数或 token 额度
压缩缓冲 buffer触发点与窗口上限之间预留的余量
溢出回退已经超窗后走的重跑或尾部裁剪路径。与显式压缩是两回事：后者要求输入先放得下
检查点 checkpoint （进阶）provider 返回的压缩块，需整体替换历史且不可跨 provider 复用
