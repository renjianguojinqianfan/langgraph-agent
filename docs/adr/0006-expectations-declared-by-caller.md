# 完成条件由调用方声明（expectation），不由模型自报

> 2026-10-01 #46 领域建模拍板，2026-10-11 第一步落地。术语见 `GLOSSARY.md`
> 「任务与产物」与「禁用词」两节。

## 决策

1. 「这个任务做完长什么样」由**调用方**在提交任务时声明，写成可机械判定的
   `expectation`；运行时状态键 `expectations`，输入面两处（REST `CreateTaskRequest`
   与 headless `--expect kind:target`）进同一个键。
2. 第一批只有两种形态：`artifact:<沙箱根相对路径>`（存在且非空）、
   `tool_success:<工具名>`（`*` = 任一工具至少成功调用一次）。没有断言 DSL。
3. **未声明 = 信息型任务**，沿用 P0-B 的 Q9 no-op PASS，判据一条不加（纯问答不被骚扰）。
4. 判不动的声明算**未通过**（fail-closed）：一条没人能验的合格线不该被读成「过了」。
5. 子任务**不继承**父任务的 expectation——验收只挂在声明的那一层。

## 为什么值得 ADR 级记录

这条决定的是「谁来定完成」，而它乍看像个可以随手换的实现细节。2026-09-30 的裁定原本
写的是「**动作类步骤**至少一次成功工具调用才允许 final answer」——由模型自己说这一步算
不算动作类。2026-10-01 领域建模把它推翻了，理由是结构性的：

- P0-B §一 的前提是「验证者必须独立于声明者」。能让模型自报「这步是动作类」，
  它就能自报成「回答类」绕过闸门——这不是理论风险，那是它唯一的分类动机。
- 本仓 `PlanStep` / `StepRecord` 里没有任何字段承载「动作类」，标签只能由 planner（一个 LLM）
  生产；而 P0-B §三 的 S2 当年**刻意绕开分类**，用「零成功产物 ∧ 零成功调用 ∧ ≥1 失败」
  这条证据式规则，注释写明就是为了「不维护任何工具读写分类清单」。旧写法等于把刚请走的
  分类又请回来。

难反转（改回自报就重新引入结构性幻觉通道）、无上下文会疑惑（今天的代码里为什么没有
「按步骤类型判定」的影子）、有真实取舍（放弃 per-step 精度换声明方的控制权）——三条都满足。

## 后果

- 判据顺序：确定性 expectation 先行，全过才轮到 grader（#46 第二步，`aux_llm` 独立裁判）；
  机械条件未过不调用裁判，不花那份钱。
- expectation 同时落进**持久化的 `Task` 记录**（读面：API / trace / 前端看得出这次声明了什么）；resume 后仍按同一条线判，靠的是 `expectations` 随 checkpoint 的状态通道恢复——`Task` 字段本身不承担续跑契约，只是让「欠了什么」在事后仍然可读。
- 交付型任务可以因为「声明的产物没写出来」落 `UNVERIFIED`（见 0005），这是 #46 要抓的
  原始现象：一次工具都没成功调用也能 `COMPLETED` 且 `exit 0`（外部活标本 eval-harness T056）。

## 重开条件

- 出现第三种 expectation 形态的需求（断言 / 内容结构 / 条数）时重开：那时要一起拍
  「谁来校验越界声明」和沙箱根之外的路径策略。
- 人工复核出口（把 `UNVERIFIED` 接受为 `COMPLETED`）落地时，声明方与判定方的关系要重述。
