# 熔断计数按运行各记一本账，不跨任务共享

> 2026-09-25 [#60](https://github.com/renjianguojinqianfan/langgraph-agent/issues/60) 拆解决定居：
> 该票的「父任务停止不传播」照修，「熔断计数每子任务独立」**判为设计如此、不修**。
> 关联 [ADR 0002](0002-moat-discipline-no-attention-reallocation.md)（冻结区与护城河纪律）。

## 决策

`ToolExecutor` 的熔断状态（`_breakers`，按工具名键控）**归每个 `AgentRuntime` 私有**，父子任务
之间、子任务相互之间都不共享。跨运行失控的兜底手段是**停止传播**（#60 保留的那半），不是共享熔断。

## 为什么值得 ADR 级记录

这是一条**隐式假设被第二种运行静默继承**的口子，不记下来就会被下一个读代码的人当成 bug 重修：

1. P0 落 `resilience.py` 时世界上只有一种运行（一个任务一个循环），账记在循环身上自然成立。
2. P1 的架构约束（`docs/incremental-arch-p1.md` 首段）明确写着「不破坏现有编排内核（含 P0 压缩 /
   熔断）」——当时正确的保守选择，代价是"一次运行 = 一本保险丝账"从未被登记为决定。
3. 共享它现在只有三条路，都不划算：改 `resilience.py`（CI 机械冻结区，需 `[OVERRIDE]` 人工批准）；
   从非冻结侧写入它的私有 `_breakers`（guard 拦不住，但一旦那层改动就**静默失效**，比走批准更坏）；
   在共享实例外加锁——`_breaker_for` 在 `dispatch` 内部，锁在 dispatch 上等于把父子工具执行串行化。
4. 子任务跑在 `ThreadPoolExecutor`（`subagent_max_concurrency`）上，"同时上好几个人"是常态，
   无锁共享一本账本身就是竞态；而 `record_failure` 是读-改-写，竞态方向是**少计数**（更难跳闸），
   一个既加了复杂度又只会漏跳的保险丝不值得。

## 影响面（照 #60 验收要求如实记）

- 同一个工具在 N 个子任务里各自失败，各吃各的 `tool_failure_threshold`，**不会合并成一次跳闸**；
  最坏额外耗时约 `并发数 × 阈值 × 单次工具超时`。
- 「单条循环不被拖死」这一原始语义不受影响——它本来就是 per-runtime 的。

## 重开条件

#58（运行流水仪表盘）上线、能观测到子任务内同一工具反复失败**真实发生**之后，再用数据评估共享方案；
届时按 `[OVERRIDE]` 走人工批准开冻结区，而不是从侧面绕。在此之前不重开。

## 顺手划走的一条

#60 票面里「子任务的 `tool_circuit_open` 事件主界面看不见」属**可见性**问题，归 #58（运行流水），
不是计数问题；本 ADR 不覆盖它。
